What is SFHealth?

SFHealth is a free, automated health audit platform for Salesforce and Marketing Cloud orgs — no setup, no agents, actionable results in under 2 minutes.

💡
The one-line pitchThink of SFHealth as an MOT check for your Salesforce org — it scans 38+ areas, scores each one, and tells you exactly what to fix and why.

The problem we solve

Most Salesforce orgs accumulate technical debt silently. Admins are busy, consultants are expensive, and there's no built-in dashboard that says "here's what's actually wrong." Orgs end up with:

  • Hundreds of unused custom fields bloating every page layout
  • Workflow rules and Process Builders that should have been migrated to Flow years ago
  • Apex classes with no test coverage sitting one deployment away from a failed release
  • Profiles with "Modify All" access that nobody remembers creating
  • Marketing Cloud automations quietly erroring out with no alert

SFHealth surfaces all of it — automatically, in one report, with a prioritised fix list.

What we check

🤖

Automation

Workflow rules, Process Builders, Flows — checks what's active vs deprecated vs broken.

🔐

Security

Profiles with excessive permissions, password policies, MFA adoption, guest user exposure.

🗄️

Data Quality

Duplicate rules, validation rules, empty required fields, unused record types.

⚡

API & Limits

Governor limit usage, API call patterns, daily request headroom.

💻

Code Quality

Apex test coverage, hardcoded IDs, inactive triggers, stale API versions.

👥

User Adoption

Login rates, inactive users, licence utilisation, last activity dates.

Who it's for

  • Salesforce Admins — get a clear picture of org debt and a fix priority list
  • Developers — catch stale Apex, missing test coverage, and deprecated APIs before they cause deploy failures
  • Architects — benchmark orgs, track improvement over time, compare across clients
  • Consultants — run a professional health check on day one of every engagement, generate a branded PDF for the client
  • Leadership / CTO — see portfolio-level fleet scores and grade distributions without reading code

Vision & Mission

Why we built SFHealth, what we believe, and where we're going.

The vision

Every Salesforce org in the world should have a health score — just like a credit score or a code coverage percentage. A single number that everyone from the intern to the CTO can understand, backed by 38+ automated checks that never need a consultant to interpret.

We believe that org health should be continuous, not a once-a-year engagement deliverable. The best time to fix a problem is before it causes a production incident, not after.

Why we built it

The founders spent years doing Salesforce implementations and repeatedly saw the same pattern: orgs that looked fine on the surface were quietly accumulating debt. Admins had no automated way to audit themselves. Consultants charged thousands for health checks that were largely manual. And when something finally broke — a governor limit breach, a failed deployment, a security audit — the cleanup cost far more than prevention would have.

SFHealth exists to make the "what's wrong with my org" question free, instant, and repeatable.

Our principles

  • Read-only always. We never write a single record to your org. Not one. If it can't be done read-only, we don't do it.
  • No password, ever. We use Salesforce's official OAuth 2.0 + PKCE flow. Your password never touches our servers.
  • Transparency over black boxes. Every score, every flag, every recommendation comes with a plain-English explanation of why.
  • Actionable, not decorative. We don't produce vanity dashboards. Every finding maps to a specific fix.
  • Free tier that's actually useful. The core audit is and will always be free. Power features (scheduling, portfolio, white-label) are premium.

The roadmap vision

Long-term, SFHealth is the Datadog for Salesforce ecosystems — a continuous monitoring platform that catches regressions the moment they happen, not months later. That means scheduled audits, real-time alerts, delta tracking between deployments, and a consultant marketplace where certified partners can offer remediation directly inside the platform.

Frequently Asked Questions

Answers to the most common questions about SFHealth.

General

Is it really free?

Yes. The core Salesforce and Marketing Cloud audits, score history, and basic trend charts are free. Advanced features like scheduled audits, portfolio management, white-label PDF reports, and custom rules are premium.

Does it write anything to my org?

No. SFHealth is strictly read-only. We use a read-only OAuth token and never attempt to insert, update, or delete any data. The Salesforce token we receive has api scope only — no write or full scope is requested.

How long does an audit take?

Typically 30–90 seconds for a standard Salesforce org. Larger orgs with thousands of Apex classes, custom objects, or users may take up to 3 minutes. Marketing Cloud audits typically complete in 60–120 seconds.

How often should I run an audit?

We recommend after every major release or deployment, and at minimum monthly for production orgs. Use scheduled audits (weekly or monthly) to automate this.

Do I need a Salesforce account to use SFHealth?

No. You can run a Salesforce audit as a guest — just connect your org via OAuth and run the audit. Creating an SFHealth account unlocks history, trend tracking, schedules, and portfolio features.

Security

Where is my data stored?

Audit results are stored in our database (PostgreSQL on Render). Your Salesforce password is never stored — we only store the OAuth access token temporarily in memory for the duration of the audit session.

Can SFHealth see my data?

SFHealth reads metadata and aggregate counts — not your actual records. For example, we count how many users are inactive, but we don't read their names into our database. Unused field detection reads field API names, not field values.

How do I disconnect?

Click "Disconnect SF" in the nav. This revokes the OAuth token at Salesforce's end via the /services/oauth2/revoke endpoint — the token is immediately invalidated.

How Scoring Works

A transparent breakdown of how your org's health score is calculated — no black boxes.

The overall score

Your org's overall score is a weighted average of six category scores, each scored 0–100. The weights reflect the relative importance of each category to production org health:

CategoryWeightWhat poor scores indicate
🔐 Security20%Exposed data, over-privileged users, weak password policies
🤖 Automation20%Deprecated tech (WFR/PB), conflicting automation, inactive flows
🗄️ Data Quality15%Missing validation, duplicate records, no duplicate rules
⚡ API & Limits15%Governor limit proximity, API abuse patterns
💻 Code Quality15%Low test coverage, hardcoded IDs, stale API versions
👥 User Adoption15%Inactive licensed users, low login rates

Grade bands

GradeScore rangeMeaning
A90–100Excellent — org is in great shape, minimal attention needed
B80–89Good — minor issues present, address in next sprint
C70–79Average — several issues to address, plan a cleanup sprint
D60–69Poor — significant debt, risk of incidents without action
F0–59Critical — immediate attention required

Issue priorities

Every finding is tagged with a priority. The priority affects both the score deduction and the recommended actions list:

  • Critical — immediate fix required, significant score impact
  • High — address within this sprint
  • Medium — address in next planning cycle
  • Low — nice to fix, minimal score impact
ℹ️
Partial scansIf some API calls fail (permission issues, API limits), SFHealth completes the audit with what it could collect and marks the result as a "Partial scan." Scores may be slightly lower than actual in partial scans.

Audit Categories

A detailed look at what each of the six Salesforce audit categories checks.

🤖 Automation

Checks the state of your org's declarative automation layer.

  • Active Workflow Rules — Salesforce is sunsetting Workflow Rules. Active WFRs are flagged as High priority.
  • Active Process Builders — Same as WFR. Any active PBs should be migrated to Flow.
  • Inactive Flows — Flows that were created but never activated, or were deactivated without being deleted.
  • Flow version sprawl — Excessive inactive versions of the same flow indicate poor lifecycle management.

🔐 Security

Checks access control, authentication policies, and exposure risks.

  • Profiles with Modify All — Any profile (other than System Administrator) that has "Modify All Data" is flagged Critical.
  • Password policy strength — Checks minimum password length, complexity, expiry, and lockout settings.
  • MFA enforcement — Whether multi-factor authentication is enforced at org level.
  • Guest user access — Over-permissioned guest profiles are a common attack vector.
  • Session security settings — Session timeout, IP restrictions, and login IP ranges.

🗄️ Data Quality

  • Duplicate rules — Whether duplicate matching rules exist on standard and custom objects.
  • Validation rules — Coverage of required business rules via validation rules.
  • Unused custom fields — Custom fields with no data in them across the entire org.
  • Record types in use — Inactive or unused record types that add complexity.

⚡ API & Limits

  • Daily API request usage — Percentage of daily API call limit consumed.
  • Bulk API usage — Whether the org is close to Bulk API limits.
  • Governor limits proximity — Any limits approaching 80% consumption trigger a warning.

💻 Code Quality

  • Apex test coverage — Org-wide Apex test coverage. Below 75% is High priority; below 60% is Critical (and will fail deployments).
  • Hardcoded IDs — Apex classes containing hardcoded Salesforce record IDs — a common migration-breaking anti-pattern.
  • Stale API versions — Apex classes and Visualforce pages using API versions older than 3 releases.
  • Inactive triggers — Triggers that exist but are not active.
  • VF page count — High Visualforce page counts may indicate legacy UI that should be migrated to LWC.

👥 User Adoption

  • Inactive users with licences — Users who haven't logged in for 90+ days but still hold active licences.
  • Login rate — Percentage of licensed users who logged in during the past 30 days.
  • Last activity — Org-wide last-activity recency check.

Salesforce Audit

How the Salesforce org audit works under the hood.

Authentication

SFHealth uses OAuth 2.0 Authorization Code Flow with PKCE (Proof Key for Code Exchange). This is the same flow used by Salesforce's own first-party apps and is the most secure OAuth flow for web applications.

What happens step by step:

  1. You click "Connect" — we generate a random code_verifier and its SHA-256 hash (code_challenge)
  2. You're redirected to login.salesforce.com with the code challenge
  3. Salesforce authenticates you and redirects back with an authorisation code
  4. We exchange the code + verifier for an access token — your password is never involved
  5. The access token is stored in server memory only for the duration of your session

What data is accessed

The audit uses only read API calls — primarily SOQL queries via the REST API, Tooling API, and SOAP API. Examples:

SELECT Id, Name, ApiVersion FROM ApexClass LIMIT 500
SELECT Id, Name, IsActive FROM WorkflowRule
SELECT DailyApiRequests FROM OrgLimits

No record data (Contacts, Accounts, Opportunities, etc.) is ever read or stored.

Required permissions

  • API Enabled (on the profile)
  • View Setup and Configuration
  • View All Data (for unused field detection — optional but improves accuracy)
  • Modify Metadata (not required — we never modify anything)

Custom Rules

Write your own audit rules that fire against every audit result.

What are custom rules?

Custom rules let power users define their own health thresholds in a simple if … then flag as … syntax. Once saved, they're evaluated against every audit you run and surface findings in a "Custom Rule Findings" card.

Rule syntax

if <field> <operator> <value> then flag as <PRIORITY>

Examples:

if apexTestCoverage < 80 then flag as CRITICAL
if activeWorkflowRules > 0 then flag as HIGH
if unusedFieldCount >= 50 then flag as MEDIUM
if criticalIssues > 0 then flag as CRITICAL

Supported fields

FieldDescription
apexTestCoverageOrg-wide Apex test coverage percentage (0–100)
activeWorkflowRulesNumber of active Workflow Rules
unusedFieldCountNumber of custom fields with no data
totalApexClassesTotal Apex class count
criticalIssuesNumber of critical-priority findings in this audit
highIssuesNumber of high-priority findings

Supported operators

>, <, >=, <=, =, !=

Supported priorities

CRITICAL, HIGH, MEDIUM, LOW

⚠️
Evaluation is client-sideCustom rules are evaluated in your browser using the audit data already on screen — no additional API calls are made. Rules are stored server-side per user account.

Technical Debt Tracker

Turn one-time audit findings into a living backlog — track, assign, and burn down org debt over time.

🔑
Requires a connected Salesforce orgThe Debt Tracker is scoped to a Salesforce org session. MC findings can also be tracked — they are stored against the currently connected SF org.

The problem it solves

Every audit produces a list of findings. Without a tracker, that list is looked at once and forgotten. The same problems reappear in the next audit, and the one after that. The Debt Tracker turns each finding into a persistent work item with an owner, a status, and a history — so debt actually gets resolved instead of re-discovered.

Adding items to the backlog

After any audit completes, every recommended action has a ⊕ Track button. Click it and the finding is instantly added to your backlog. The button turns ✓ Tracked (green) immediately. If an open item already exists for that exact finding, you get "Already tracked" — no duplicates are ever created.

This works for both Salesforce audit findings and Marketing Cloud audit findings.

The backlog

Navigate to Debt Tracker in the top navigation. The page shows:

  • Stat row — Open, In Progress, Resolved, and Critical Open counts at a glance
  • Burndown chart — Weekly line chart: red = items added, green = items resolved. When green meets red, you're burning faster than you accumulate
  • Backlog list — All items sorted Critical → High → Medium → Low

Managing items

1

Change status inline

Each item has a Status dropdown — click it and select Open, In Progress, or Resolved. Saves immediately. Resolved items show the resolution date.

2

Assign to a team member

Click the Assignee field, type a name or email, and click away. Saves on blur — no submit button needed.

3

Filter the backlog

Use the filter bar to narrow by Status, Priority, or Category. Hit Filter to apply. Combine filters freely.

4

Delete an item

Click Delete on any item and confirm. Use this for false positives or items you've decided not to track.

Jira integration

Push any debt item directly to Jira as a new issue. Click the Jira button on an item and enter:

  • Jira Base URL — e.g. https://yourcompany.atlassian.net
  • Email — your Atlassian account email
  • API Token — from id.atlassian.com → Security → API Tokens
  • Project Key — e.g. SFDEV

SFHealth creates the Jira issue with the finding text, category, priority, and org ID pre-populated. The resulting issue key (e.g. SFDEV-42) appears as a blue badge on the debt item.

🔒
Credentials are never storedYour Jira API token is sent directly to Atlassian on the server side and is not saved in SFHealth's database. You enter it fresh each time you push.

Linear integration

Push any debt item to Linear. Click the Linear button and enter:

  • Linear API Key — from Linear → Settings → API → Personal API Keys
  • Team ID — the UUID from Linear → Settings → Teams → [Your Team] → General

A Linear issue is created with title, description, and priority mapped (Urgent / High / Medium / Low). The same no-storage policy applies — credentials are per-request only.

Burndown chart explained

The chart plots two weekly series:

  • Red line — new debt items added per week
  • Green line — items resolved per week

A healthy team's green line trends upward and eventually crosses the red line. If the red line is always higher, debt is growing faster than the team can address it — a signal to either reduce the number of new issues introduced or allocate more remediation capacity.

Security Model

How SFHealth keeps your org data secure.

OAuth 2.0 + PKCE

We use the Authorization Code flow with PKCE — the industry-standard secure OAuth flow. PKCE prevents authorisation code interception attacks. No client secret is exposed to the browser. The code verifier is stored in a short-lived cookie that expires in 10 minutes.

Token handling

  • Access tokens are stored in server memory only — never in a database, never in a cookie
  • Tokens are scoped to api only — no write access is ever requested
  • On logout, the token is immediately revoked at Salesforce's endpoint
  • Session cookies are httpOnly, sameSite: lax, and secure in production

Infrastructure

  • Hosted on Render — SOC 2 compliant infrastructure
  • All traffic over HTTPS — TLS 1.2+
  • Rate limiting on all API endpoints
  • Helmet.js security headers on every response
  • No third-party analytics or tracking scripts

MC credentials

Marketing Cloud Client IDs and Secrets are encrypted with AES-256-GCM before being stored in the database. The encryption key is an environment variable that never touches the database.

Data & Privacy

What data we collect, what we store, and what we never touch.

What we store

  • Aggregate counts and scores (e.g. "42 unused fields", "security score: 68")
  • Metadata names — Apex class names, Flow names, field API names
  • Your SFHealth account email and hashed password (bcrypt)
  • Audit timestamps and history

What we never store

  • Your Salesforce password (we never see it)
  • Record data — Contacts, Accounts, Leads, Opportunities, custom object records
  • PII from your Salesforce org
  • OAuth access tokens (in-memory only, gone on restart)

Data retention

Audit history is retained indefinitely unless you delete it. You can delete your account and all associated data from the Profile settings page.

Subprocessors

  • Render — Hosting and database (PostgreSQL)
  • OpenRouter / Groq — AI remediation guide (only the audit findings summary is sent, never org credentials)

Glossary

Key terms used throughout SFHealth.

A

API Enabled — A Salesforce profile permission required to make REST/SOAP API calls. Required for SFHealth to run an audit.

B

Burndown Chart — A weekly line chart in the Debt Tracker showing new debt items added (red line) vs. items resolved (green line). When the green line trends upward and crosses the red line, the team is resolving debt faster than it accumulates.

C

Compliance Report — A print-ready audit document generated from a Salesforce audit. SFHealth produces three types: GDPR/DPDP, SOC 2 Readiness, and ISV/AppExchange Security. Intended to support compliance preparation, not replace formal assessments.

D

Debt Item — A single tracked finding from an audit. Stored in the Debt Tracker backlog with a status (Open / In Progress / Resolved), priority, category, optional assignee, and optional Jira or Linear issue link.

F

Fleet Score — The average health score across all orgs in your portfolio. Visible in the Portfolio view.

Flow — Salesforce's current-generation declarative automation tool. Replaces Workflow Rules and Process Builder.

G

Governor Limits — Salesforce's execution guardrails — limits on SOQL queries, DML operations, CPU time, heap size, and API calls per 24-hour period.

Grade — A letter grade (A–F) derived from the overall score. A = 90–100, B = 80–89, C = 70–79, D = 60–69, F = below 60.

M

MID — Marketing Cloud Account ID. Used to identify a specific business unit in a multi-BU Marketing Cloud account.

O

OAuth 2.0 PKCE — Proof Key for Code Exchange. A security extension to OAuth that prevents authorisation code interception. Used by SFHealth for all Salesforce connections.

Org — A Salesforce environment instance. A company may have multiple orgs: production, sandboxes, developer orgs.

P

Partial Scan — An audit where some API calls returned errors (permission issues, rate limits). The score is calculated from available data and may be lower than the actual score.

PKCE — See OAuth 2.0 PKCE.

Process Builder — A deprecated Salesforce automation tool. Salesforce recommends migrating all Process Builders to Flow.

S

SAP — Sender Authentication Package. A Marketing Cloud configuration that sets up a private domain, dedicated IP, and reply mail management for email sending.

Score — A 0–100 number representing org health. Calculated as a weighted average of six category scores.

Source Finding Key — A hash derived from an audit finding's category and action text. Used to prevent duplicate debt items — if an open item with the same key already exists, a second ⊕ Track click returns "Already tracked" instead of creating a duplicate.

T

Technical Debt — Accumulated shortcuts, misconfigurations, deprecated automation, and code quality issues in a Salesforce org. The Debt Tracker turns SFHealth audit findings into a managed backlog to reduce this debt over time.

W

Workflow Rule — A legacy Salesforce automation tool, predecessor to Process Builder and Flow. Being retired by Salesforce.
